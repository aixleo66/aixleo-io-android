# 文档维护约定

默认文档跟随当前分支；使用某个旧提交时，应阅读该提交里的文档。通用要求无需每次升级替换版本号，但也不承诺永远不变：功能、接口、默认值、权限、依赖或数据流程改变时，更新对应页面并说明升级影响。

| 文档 | 内容 | 何时更新 |
| --- | --- | --- |
| README、构建、观察台、Gateway、隐私等指南 | 当前代码的用途、行为、架构边界和操作方式 | 对应行为变化时；不随 App 版本号机械改写 |
| CHANGELOG | 新增、修复、行为变化、兼容性或升级注意项 | 变化先记入 Unreleased，实际交付时归入对应版本 |
| AUDIT 索引与 `audits/日期-版本.md` | 精确版本/提交、产物哈希、环境、通过与未通过项 | 新审核或测试后增加记录并更新索引 |
| COMPATIBILITY | 带版本、设备、系统和条件的真实覆盖 | 新增覆盖或发现兼容性变化时，保留历史范围 |
| SECURITY、许可与第三方说明 | 安全设计、保留风险、权属及依赖来源 | 机制、风险、依赖、来源或许可事实改变时 |
| RELEASE-CHECKLIST | 分发内容和重复使用的交付流程 | 分发范围或流程改变时 |

## 版本与证据

- 不把审核记录中的版本、哈希、测试数量和日期改成新版本；新结论另建记录。历史更正要写明日期与依据。
- 修复某个缺陷时，可以明确标注“自某版本起修复”或受影响范围；这类版本号有实际含义，应保留。
- JDK、Android SDK、厂商依赖、协议及许可证的版本是兼容性或权属信息，不属于需要去掉的 App 版本文案。
- 当前分支有新代码，不等于最新审核已覆盖这些代码；没有对应证据的部分标为待验证。
- 每次源码快照生成自己的 `source-manifest.json`；历史审核链接到对应提交的清单，避免被未来清单覆盖。

## 中英文同步

`docs/cn` 与 `docs/en` 保持相同的相对文件路径。行为变化时同步修改对应页面，保留语言切换、代码示例、参数、限制和测试状态的一致性。根 README 默认中文；旧入口保留有效链接。不要翻译或改写第三方许可证原文。

## 每次版本迭代

通常只需：补充变更记录、更新受影响的指南、记录适用测试并更新审核/兼容性索引。没有变更的页面无需重写。当前不为每个小版本复制整套文档；需要旧版时通过 Git 提交查看。将来若并行维护多个不兼容版本，再考虑发布分支或版本化文档站；这不表示现在要创建标签或 Release。

参考：[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) 将未发布变化集中管理；[Django 的发布流程](https://docs.djangoproject.com/en/4.2/internals/release-process/) 区分开发分支与稳定版本文档的维护。此处采用适合当前项目规模的简化方式。
