# 0.2.1 features and validation limits

[简体中文](../cn/FEATURES-0.2.1.md) | [English index](README.md)

This is an unofficial Android research app for RayNeo iO. It remains app-oriented and does not provide a stable standalone AAR. Implementation and validation on particular devices are different claims. The main device baseline used Strix OS 1.0.4.12, with official App 1.0.4 as a comparison. Revalidate after changing firmware, phone or operating system.

| Feature | Current implementation | Validation and limits |
| --- | --- | --- |
| Connection | Remembers a paired device and establishes an authenticated session; nearby-device events and phone startup can trigger recovery attempts | Single-day nearby and reboot recovery cases passed. Overnight and in-use stability remain incomplete; Android background policies affect recovery. |
| Assistant | Glasses microphone audio goes to user-configured cloud ASR and answer services; answers return to the glasses. Supports a short follow-up window and some voice tasks | Real Q&A and selected follow-up cases passed. Natural-language actions mostly use explicit rules, not general intent understanding. |
| Recording | Started from the phone or native glasses menu; saved locally as Ogg Opus and playable on the phone. Ordinary recording does not automatically transcribe | Minute-scale saving, playback and seeking passed. Longer recording, disconnection recovery, pause/resume and audio-direction handling remain incomplete. |
| Todos | Stores todos on the phone and synchronizes the whole list to the glasses. Completion in the native glasses list returns to the phone. Explicit assistant create-todo phrases spoken through the glasses create an item on the phone and sync it back | A 13-item baseline, selected additions/deletions/completions and explicit voice creation passed. Direct creation in the native glasses list, concurrent conflicts, large lists, reminders and cloud-account sync remain incomplete. |
| Weather and time | Phone-location weather; pushes temperature when ready and on an approximately 15-minute schedule; synchronizes the phone clock | Temperature after connection and limited scheduling checks passed. All-day background behavior, location changes and OS restrictions need further validation. |
| Notifications | Reads system notifications from user-selected apps and forwards them; uses markers to filter foreground-service persistent notices | The source app must first post a real system notification. In-place updates and visibility across screen states are not fully accepted. The new 0.2.1 check uses `FLAG_FOREGROUND_SERVICE` or category `service`; existing ongoing, group-summary and silent filters still apply. One real-device “SMS is running” notice was forwarded; its flags were not captured and the cause remains unconfirmed. A user reported that disabling the corresponding system notification channel stopped it. Similar notices from other apps have not been specifically tested. |
| Device settings | Reads device state/configuration; exposes limited controls for brightness, screen timeout, crown direction and head-up wake | Limited write/readback checks do not establish support for every official control. Height/distance and do-not-disturb writes remain incomplete. |
| Charging case | Observes in-case, lid and case-battery states | Continuous battery refresh while charging is unconfirmed. |

A successful send means the app/communication layer completed its operation; it does not prove that content appeared on the lens. Visual behavior requires wearer observation. See [testing](TESTING.md) for reproduction and [developer capability map](CAPABILITY-MAP.md) for source locations and parameters.

Compared with the early public preview, the main changes are Ogg Opus instead of the older WAV recording flow, phone–glasses todo sync, weather and time, more device settings, automatic reconnection and the persistent-service notification filter introduced in 0.2.1. The difference between 0.2.0 and 0.2.1 itself is only the notification rule. Officially visible features not implemented here are listed in the [device capability reference](DEVICE-CAPABILITIES.md).
